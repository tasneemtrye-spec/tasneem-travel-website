# تصميم إدارة قاعدة معرفة مساعد تسنيم من لوحة الإدارة

**الحالة:** تصميم ومراجعة قبل التنفيذ الحي  
**التاريخ:** 2026-11-16  
**الفرع:** feature/assistant-knowledge-admin-design-2026-11

## الهدف
تمكين حساب الإدارة المعتمد من مراجعة وتحرير الأسئلة الشائعة ومعلومات الوكالة والخدمات والوجهات التي يعتمد عليها مساعد تسنيم، مع سجل تحديث واضح، دون خلط المحتوى بطلبات الحجز أو كشف مفاتيح الخدمة في المتصفح.

## نتائج فحص الوضع الحالي
- لوحة `/admin.html` تستخدم Supabase Auth ومفتاح publishable، وتتحقق من بريد الحساب الإداري قبل إظهار الواجهة.
- حماية البيانات الفعلية لطلبات الحجز تعتمد RLS؛ إخفاء الواجهة وفحص البريد في JavaScript ليسا حدّاً أمنياً.
- جدول `public.booking_requests` مخصص لطلبات العملاء فقط.
- الجدول `public.booking_rate_limits` مخصص للحد من الطلبات.
- لا يوجد حالياً جدول لقاعدة معرفة المساعد.
- سياسات طلبات الحجز تستخدم الدالة `public.is_tasneem_admin()`، وهي دالة SQL مستقرة بصلاحيات المستدعي، وتتحقق من بريد JWT الإداري `tasneemtrye@gmail.com`.
- لا توجد حاجة لمنح صلاحيات على بيانات الحجوزات لإدارة محتوى المساعد.

## التصميم المقترح

### 1. جدول مستقل
إنشاء جدول منفصل باسم `public.assistant_knowledge` بسجل وحيد:
- `id`: قيمة ثابتة مثل `tasneem` ومفتاح أساسي.
- `content`: مستند JSONB يضم `agency`, `services`, `destinations`, `faq`, `booking_process`, `privacy`, `limitations`.
- `version`: رقم إصدار صحيح موجب.
- `updated_at`: وقت آخر تعديل.
- `updated_by`: UUID لحساب الإدارة الذي نفذ التعديل.

لا توضع بيانات العملاء أو الطلبات في هذا الجدول. ولا تضاف أسعار أو شروط تأشيرات أو توافر إلا بعد اعتماد مصدر رسمي وتاريخ صلاحية واضح.

### 2. حماية قاعدة البيانات
- تفعيل RLS على الجدول.
- منح `authenticated` فقط الصلاحيات اللازمة للقراءة والإضافة والتحديث؛ لا تمنح `anon` أي صلاحية.
- سياسات SELECT وINSERT وUPDATE تشترط `public.is_tasneem_admin()`.
- سياسة UPDATE يجب أن تتضمن الشرط في `USING` و`WITH CHECK`.
- لا تُنشأ سياسة DELETE في الإصدار الأول؛ التراجع يكون بإصدار سابق موثق.
- لا يستخدم `user_metadata` للتفويض، ولا يوضع service-role أو secret key في `admin.html`.
- يلزم فحص RLS وامتيازات الجدول بعد تطبيق الترحيل، ثم اختبار مستخدم مجهول ومستخدم مسجل غير إداري وحساب الإدارة.

### 3. واجهة الإدارة
إضافة قسم مستقل بعنوان «معرفة المساعد الذكي» داخل لوحة الإدارة بعد التحقق من جلسة الإدارة:
- عرض نسخة المحتوى الحالية ورقم الإصدار وتاريخ آخر تحديث.
- تحرير الأسئلة الشائعة وإضافة/تعديل/تعطيل سؤال.
- تحرير بيانات التواصل والخدمات والوجهات مع قيود طول ومدخلات واضحة.
- معاينة JSON قبل الحفظ والتحقق من البنية المطلوبة.
- زر حفظ مع رسالة نجاح/فشل واضحة، وعدم فقد التعديلات عند فشل الشبكة.
- عدم عرض أو تعديل أي سجل من `booking_requests` من هذا القسم.

### 4. ربط المساعد بمصدر المعرفة
لا يكفي حفظ البيانات في Supabase؛ يجب أن يقرأ Worker المعرفة المنشورة من مصدر موثوق:
- الخيار المفضل: endpoint خادمي محمي يقرأ النسخة النشطة ويعيد محتوى عاماً منزوع الحقول الإدارية، أو نشر نسخة معرفة معتمدة إلى Worker.
- لا تجعل Worker يعتمد على مفتاح service-role في المتصفح.
- لا تعرض محتوى المسودات للزوار؛ يلزم فصل «حفظ المسودة» عن «نشر المعرفة».
- عند النشر، تحقق من بنية JSON، حجم المحتوى، وحقول الاتصال، وسجل رقم النسخة.
- احتفظ بآخر نسخة صالحة في Worker عند فشل جلب النسخة الجديدة.

## شروط التنفيذ والاختبار
1. الحصول على موافقة منفصلة قبل تغيير مخطط Supabase الحي أو سياسات RLS.
2. إعداد migration ومراجعتها في Pull Request قبل التطبيق.
3. التحقق من صلاحيات `is_tasneem_admin()` ومن عدم اعتماد التفويض على بيانات user-editable.
4. اختبار RLS بثلاث حالات: anon مرفوض، authenticated غير إداري مرفوض، حساب الإدارة مسموح.
5. اختبار تحرير FAQ، الحفظ، إعادة التحميل، فشل الشبكة، والرجوع إلى نسخة سابقة.
6. اختبار أن واجهة الحجز وقراءة الطلبات وتحديثها لم تتأثر.
7. اختبار Worker بعد ربط مصدر المعرفة، مع التأكد من عدم اختراع الأسعار أو الشروط أو التوافر.
8. لا دمج إلى `main` ولا نشر Pages/Worker دون الموافقة المنفصلة المطلوبة في دليل تشغيل المشروع.

## قرار المرحلة الحالية
هذا الملف يوثق التصميم بناءً على المخطط والسياسات الحية التي تمت قراءتها. لم يتم إنشاء جدول أو تعديل سياسة أو تغيير بيانات أو نشر أي خدمة. الخطوة التنفيذية التالية هي إعداد ترحيل SQL وواجهة الإدارة على فرع مراجعة، ثم تطبيق الترحيل بعد الموافقة الصريحة.
